Quando usar

Um único primário por tela — a ação que conclui a tarefa. Tonal para ações de apoio recorrentes, texto para ações terciárias e cancelamento.

Evitar

Dois primários lado a lado, rótulos genéricos ("OK", "Enviar"), largura menor que 88px e altura abaixo de 44px em mobile.

04 — Status

Badges: todo status é um badge

Quando usar

Qualquer estado de registro (pedido, fatura, usuário, integração). Fundo soft + texto na cor sólida + ícone opcional. Sempre com texto — cor nunca carrega o significado sozinha.

Evitar

Badge clicável (isso é chip ou botão), mais de 3 palavras, mais de um badge de status por linha e cores fora da paleta semântica.

05 — Entrada de dados

Campos de formulário

Usado para login e notificações.
Mínimo de 8 caracteres.
Cupom válido — 15% de desconto.
Quando usar

Campo preenchido é superfície, não caixa com borda. Foco marca a base em 2px na cor primária. Erro e sucesso trocam a superfície e mostram mensagem com ícone.

Evitar

Placeholder como rótulo, validação a cada tecla, mais de uma coluna em mobile e mensagens de erro genéricas.

Implementação 
<TextField label="E-mail"
  icon={Mail} state="error"
  hint="Mínimo de 8 caracteres" />

Quando usar

Switch para efeito imediato, sem salvar. Checkbox para múltipla escolha em formulário. Radio para 2–5 opções exclusivas. Segmentado para alternar visão de conteúdo.

Evitar

Switch que só aplica após "Salvar", radio com uma opção só, mais de 5 radios (use select) e slider para valores que exigem precisão.

Quando usar

Tabs para 2–5 visões irmãs do mesmo objeto. Accordion para conteúdo longo e opcional (FAQ, configurações avançadas). Stepper para fluxo linear com validação por etapa. Breadcrumb só em hierarquia com 3+ níveis.

10 — Feedback

Alertas, modal, toast, tooltip e estado vazio

Alertas inline
{{ al.title }} {{ al.body }}
Overlays

Nenhum pedido ainda

Quando o primeiro pedido entrar, ele aparece aqui com status e histórico.

Quando usar

Alerta inline para condição persistente no contexto. Toast para confirmação passageira (4s, com desfazer). Modal só para decisão bloqueante ou destrutiva. Tooltip para explicar ícone.

Evitar

Modal para confirmar sucesso, dois toasts simultâneos, tooltip com informação essencial e alerta vermelho para aviso não crítico.

Quando usar

Até 1s: nada ou spinner no botão. 1–3s: skeleton com a forma do conteúdo real. Acima de 3s ou processo com identidade (upload, emissão fiscal): Lottie + mensagem do que está acontecendo.

Evitar

Spinner de tela cheia, skeleton que não corresponde ao layout final, Lottie pesado (>60KB) e barra determinada com percentual falso.

Quando usar

Calendário completo para escolher/revisar datas com contexto visual (vencimentos, agenda). Campo com popover para uma data única em formulário compacto. Atalhos de período para relatórios recorrentes.

13 — Adaptação por plataforma

Web, Windows, Android e iOS

Os tokens (cor, tipografia, raio, motion) são os mesmos em toda plataforma. O que muda é a métrica de layout: margens, largura de conteúdo, breakpoints e alvo de toque — para a interface nunca quebrar ou parecer estranha no ambiente nativo.

Moldura de referência
{{ pfFrameCaption }}
{{ sp.label }} {{ sp.value }}

{{ pfNote }}

Quando usar cada faixa

Web: layout fluido com largura de conteúdo máxima e grid de 12 colunas. Windows: janela redimensionável, nunca assuma altura/largura fixa. Android/iOS: uma coluna, navegação por polegar, sempre respeitando os insets seguros do sistema (notch, barra de gestos, status bar).

Evitar

Pixels fixos fora do grid da plataforma, alvo de toque abaixo do mínimo nativo, conteúdo colado à borda sem margem de segurança e ignorar a orientação retrato/paisagem em mobile.
